# T3 filesystem capability probe

Date: 2026-11-15. Device: SM-S936B, Android 17 / API 37, One UI 9.
Engine: NewBlackbox `89b5983` + patches 0001 + 0004 + 0005, UID 10057.

**Method:** `phase0b/scripts/fs-probe.sh` pipes `t3-device.sh` into
`adb shell run-as top.niunaijun.blackbox sh -s` (domain `runas_app`), then the
guest side runs in a Canary clone (domain `untrusted_app_27`) via the T3 probe
in Canary v0.3 (key **T** on the env page). The probe creates and deletes its
own folders under `blackbox/dualfs-probe/` and the guest's `files/t3probe/`.

## Decision table

| Decision | Result | Why |
|---|---|---|
| **Tag storage** | **xattr** (`user.dualapp.blob`) | `setfattr` / `getfattr` work on L-ext and from the guest; the tag survives a rename. No index fallback needed. |
| **Pool location** | **external** (engine external files, same FUSE mount as the trees) | L-ext and L-guest have `st_dev=182`; L-int has `st_dev=65099`. A raw `rename(2)` across them fails with `EXDEV`. Harvest moves files, so the pool must share the trees' mount. |
| **Move MLBB's external data to internal?** | **No** | Sparse files, xattrs, inotify and `copy_file_range` all work on the external path. No engine behavior change, so no cached-path breakage (N1). |

## Findings that affect later tasks

- **M8 is viable on the external path.** Sparse placeholders cost 0 data blocks, xattrs work as the tag, and `copy_file_range` is fast enough for copy-up. This is the best possible T3 result for the storage design.
- **The pool must live on the external FUSE mount**, next to the trees, because cross-mount `rename(2)` is `EXDEV`. The planned pool path (`<engine external files>/blackbox/dualfs/pool/...`) already satisfies this.
- **Symlinks are impossible on the external path.** M1 (symlink farm) is dead there; M8 does not use symlinks.
- **`io_uring` is fatal, not just blocked.** Android's seccomp policy kills a guest that calls `io_uring_setup`. MLBB and Instagram are unlikely to use it, but the audit should note it.
- **The inotify watch limit is not readable** from the app or the shell on this firmware. Events work; if the limit turns out to be too small in T4, `dfaudit` can watch a rotating subset of folders.
- The two guards M8 needs are confirmed: a guest can `fchmod` a read-only handle and reopen it for writing through `/proc/self/fd`. T6 cases C4/C5 must cover exactly that.
